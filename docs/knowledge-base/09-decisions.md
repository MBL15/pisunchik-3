# 9. Решения, ограничения, развитие

## Ключевые решения

| Решение | Почему | Цена |
|---|---|---|
| **Три сервиса по границам данных** (люди / соревнования / UI) | Реестр и календарь развиваются независимо; падение одного не кладёт остальное | Сетевые вызовы между сервисами, согласованность только на уровне шлюза |
| **Хранилища в памяти + сид при старте; опционально Postgres** | Без настройки — мгновенный старт и воспроизводимая демонстрация; с `FSP_DATABASE_URL` — персистентность без смены доменного кода | Работа идёт с объектами в памяти, БД — write-through снимок (JSONB) после не-GET запросов; нет транзакций между сервисами и нормализованной схемы |
| **Весь стек в Docker Compose** | `docker compose up -d --build` — Postgres + 3 сервиса одной командой | Порты 8000–8002 должны быть свободны; без live-reload |
| **Сроки в сиде — смещения от «сегодня»** | В любой день есть истёкшие/критичные/предупреждающие сроки | Для скриншотов нужен `FSP_DEMO_TODAY` |
| **Шлюз — единственная точка доверия** | Роли и личность проверяются в одном месте; сервисы проще | Сервисы доверяют заголовкам/полям шлюза — их нельзя выставлять наружу |
| **Подписанные cookie вместо серверных сессий** | Нет хранилища сессий, шлюз без состояния | Сессию нельзя отозвать до истечения 12 ч (активная роль перепроверяется на каждом запросе) |
| **Allowlist для публичного прокси** | Наружу видны только явно перечисленные эндпоинты без персональных данных | Новый публичный эндпоинт надо добавлять вручную |
| **HTML-first: Jinja + формы + редиректы** | Работает без JS, просто тестировать (e2e ходит как браузер), быстро на слабых устройствах | Интерактив — только прогрессивным улучшением |
| **Эффекты на data-атрибутах в одном скрипте** | Повторное использование без сборки; единые правила reduced-motion и no-JS | Скрипт `base.html` растёт; нет модульности |
| **Tailwind через CDN** | Без Node и сборки | Нужен интернет; в продакшене стоит собрать CSS |
| **Шлюз разделён на общий слой и разделы** (`web.py`, `listing_ui.py`, `routes/*`) | Большие разделы (реестр, модерация, журнал, лента) правятся независимо от кабинетов; общий код — в одном месте | Кабинеты, сборные и документы пока в `main.py` (~950 строк) — следующие кандидаты на вынос |
| **Списки фильтруются и режутся на страницы в сервисах** (`shared/listing.py`) | Шлюз получает только нужную страницу и фасеты; одна семантика поиска и «последней страницы» везде | Без индексов БД: снимок в памяти перебирается на каждый запрос |
| **Чистые движки** (`fsp_id`, `log_parser`, `rating`) без I/O | Юнит-тесты без сети; сидированные и загруженные протоколы проходят один путь | — |
| **Протокол формируется, а не набирается** | Федерация вносит только показатели участников с одобренными заявками (или грузит лог) — места, DSQ и баллы считает один движок `rank_entries`; ошибок переноса нет | При ручном вводе ICPC нет лога задач: равные (решено, штраф) делят место без тай-брейка по времени |
| **Рейтинг считается на лету** | Всегда актуален, настройки применяются мгновенно | O(протоколы × участники) на запрос — приемлемо для региона |
| **Код справки = HMAC** | Проверка подлинности без базы выданных документов | Смена `FSP_SECRET_KEY` делает старые коды недействительными |
| **Пароли — PBKDF2-SHA256** (`sportsman_service/security.py`) | Стандартная библиотека, без зависимостей | Для демо-аккаунтов один общий хеш (быстрый старт) |

## Известные ограничения

- **БД — снимок, а не нормализованная схема.** Состояние хранится JSONB-документами; запись после каждого не-GET запроса
  переписывает только изменённые строки (diff по хэшу), без транзакций между сервисами и без миграций. Параллельные записи
  из нескольких реплик сервиса не поддерживаются. В режиме без `FSP_DATABASE_URL` всё сбрасывается к сиду.
- **Нет ограничения попыток входа** на `/api/v1/auth/verify`.
- **id создаются как `len(...) + 1`** (например, заявки в `competition_service/main.py`). Без удаления это
  корректно, но при появлении удаления или параллельных запросов нужны последовательности БД (в Postgres-режиме счётчики сохраняются в `*_meta`).
- **Секрет по умолчанию** `dev-only-fsp56-change-me` — вне dev обязательно задать `FSP_SECRET_KEY`.
- **Служебная аутентификация шлюза — опциональная.** При заданном `FSP_SERVICE_TOKEN` сервисы принимают только запросы с
  заголовком `X-FSP-Service-Token` (`shared/service_auth.py`, `/health` открыт). В compose токен включён, а порты сервисов наружу не
  публикуются; при локальном `run_all.py` проверки нет (сервисы слушают 127.0.0.1). В продакшене — mTLS или ротация токена.
- **Статусы соревнований** меняются при создании, публикации протокола (→ FINISHED) и вручную федерацией
  (открытие / закрытие приёма заявок). Автоматических переходов по датам (→ LIVE, → FINISHED) нет — они заданы сидом.
- **Пороги ЕВСК рабочие**: `EVSK_REQUIREMENTS` масштабирована под демо-протоколы и не заменяет действующую ЕВСК
  (нет возрастных ограничений, проверки числа выполнений и квалификации судей). Нужна сверка перед боевым использованием.
- **Численность — по `start_year`**: данных о выбытии нет, поэтому спортсмен считается занимающимся с года начала занятий
  и далее; разряд в прошлых годах берётся по текущей записи профиля (занижен).
- **Проект приказа — шаблон**: текст и реквизиты нужно согласовать с министерством; издатель задан константой `ORDER_ISSUER`.
- **PDF требует системный шрифт с кириллицей** (Arial / DejaVu / Liberation или `FSP_PDF_FONT`); без него выгрузка PDF отвечает `503`.
- **Сборная — снимок**: место, баллы, разряд и тренеры фиксируются при включении в состав и не пересчитываются.
- **Live — эмуляция**: тик 1.5 с проигрывает сидированный лог; реального приёма событий с площадки нет.
- **Опрос вместо push**: live-блок опрашивает `/partials/live` раз в 2.5 с (на Windows это мешает
  live-reload, см. [runbook](08-dev-runbook.md#типовые-проблемы)).
- **Уведомления: лента в кабинете + Telegram** (`gateway_service/notify.py`; бот из `.env`: `FSP_TELEGRAM_TOKEN`, `FSP_TELEGRAM_BOT`, привязки в `.telegram_links.json`). Email не реализован. Без Postgres лента живёт в памяти sportsman и при перезапуске сбрасывается к сиду. Сроки отчётов (`REPORT_DEADLINES`) — рабочий перечень, даты сверить с министерством.
- **Большие списки фильтруются в памяти сервиса** (без индексов): на десятках тысяч записей это быстро, для сотен тысяч
  нужны запросы к Postgres с индексами вместо снимка в памяти. Журнал хранит последние 5000 записей на сервис.
- **Нет восстановления пароля и подтверждения email.**

## Дополнительные сценарии (Д1–Д12)

- **Записи без отдельных таблиц.** Нормативы, группы, журнал, апелляции, премии и токены интеграций лежат в `ExtTables` (`shared/ext.py`) — именованные JSON-таблицы
  с автонумерацией, которые целиком попадают в строку `*_meta` и в Postgres-снимок. Структуру проверяют pydantic-модели модуля при создании записи.
- **Показатели считаются на момент действия.** Результат норматива хранит порог своего времени, ходатайство — снимок списка и размеров, протокол — список корректировок.
- **Возраст допуска считается на дату старта** (`shared/domain.age_group_fit`), а не на сегодня.
- **Корректировка протокола** переводит итоги в ручной режим (`source=manual`), сохраняя исходный лог: места пересчитываются, а след остаётся в `corrections`.
- **OIDC** держит коды и токены в памяти шлюза, а клиентов — в реестре; подпись id_token — RS256 (`.oidc_key.pem`). PKCE обязателен для всех клиентов.

## Направления развития

1. **Хранилище**: PostgreSQL + миграции; репозитории вместо `store.py` с тем же интерфейсом.
2. **Безопасность**: отзыв сессий, rate limit на вход, CSRF-токены в формах (сейчас защита только `SameSite=Lax`),
   обязательный секрет из окружения. Уже сделано: служебный токен между сервисами, флаг `Secure` у cookie при https-адресе
   (`FSP_COOKIE_SECURE`), закрытые порты в compose.
3. **Автоматизация календаря**: планировщик статусов по датам, закрытие приёма заявок.
4. **Уведомления**: напоминания за 90/30 дней о сроках разрядов и категорий, о решениях по заявкам.
5. **Live**: приём событий от тестирующей системы (webhook/SSE), push вместо опроса.
6. **Сборка фронтенда**: локальный Tailwind CLI, вынос скрипта эффектов из `base.html` в модуль.
7. **Интеграции**: выгрузка протоколов и рейтинга в форматы федерации, импорт реестра.
8. **Наблюдаемость**: структурные логи, метрики, трассировка запросов через шлюз.
